00gmail-triage-bot

It went quiet. Nothing had crashed.

One Gmail OAuth grant expired. The workflow engine's answer to a failing node is to stop the execution — so a single expired token took the whole bot offline, and the only symptom was an inbox that stopped being mentioned.

gmail-triage-bot turns unread mail into Telegram cards you can act on in one tap, and drafts replies you approve before they exist in Gmail. The rewrite's first requirement was not a feature — it was that this particular silence can never happen again.

01the silence

Stopping is not error handling

A halted execution and a healthy idle bot look identical from the outside: no messages either way. That is what made it expensive — the failure was not loud enough to notice, and not quiet enough to be harmless.

02the guarantee

Every cycle is allowed to fail

One bad message, a Gmail hiccup, a Telegram timeout — each ends that cycle and nothing more. The process is not something a single malformed email gets to end.

Expired grantyou get a re-auth card, loop continues
Any cycle errorlogged, retried next cycle
Recoverya later cycle, once the token is back
Missing config keyrefuses to start, names the key

The last row is the opposite discipline on purpose. A transient failure should be survived; a misconfigured deploy should not be — running half-blind is how you get a bot that looks alive and does nothing.

03the race

The reply target that existed and didn't

Reply buttons carried a message id. Fetching by that id works for a standalone message and 404s the moment the message lives inside a thread — so "Draft reply" failed intermittently, depending on a shape nobody had thought to vary while testing.

04the draft

Nothing exists in Gmail until you say so

The model writes a reply; you read it in Telegram. Only when you accept does a real Gmail draft appear on the thread — and even then it is a draft, waiting in a client you already trust. The bot never sends mail.

Model writesa preview card in Telegram
Regenerateasks for a meaningfully different take
Accepta real Gmail draft on the thread
Sendyou, in Gmail, later

The signature block is fixed and non-negotiable, and the identity inside it — name, address, phone — is injected from config. That started as a rule about tone and turned out to be what made the repository publishable: nobody's contact details are in the source.

05the seam

One function stands between you and a vendor

Draft generation depends on a single contract: build_draft_builder(config) returns something with one generate(thread_context, prev_draft) method. Retiring the Anthropic key meant adding a second implementation and flipping the default.

The contractone factory, one method
Untouched by the swapprompt, cards, accept flow
Old providerstill selectable, not deleted
Model idsverified against the live API

That last line is not pedantry. A guessed model id fails at request time, in production, on a bot whose whole promise is that it does not go quiet.

06the inbox

A card per unread, three buttons

Every unread message in Primary becomes one Telegram card with Mark read, Trash and Draft reply. The point is not that it is faster than the Gmail app — it is that triage stops requiring you to open a place where everything else is also waiting.

Scopeunread, Primary only
Per messageone card, three actions
Destructive actionTrash, which Gmail can undo
Configone env file, fail-loud on a missing key
07build

100 tests, and none of them reach Gmail

Gmail, Telegram and the model are faked at the boundary, so the suite runs on a fresh clone with no OAuth and no keys — including the poll loop's failure paths, which are the parts that matter and the hardest to provoke against a live account.
